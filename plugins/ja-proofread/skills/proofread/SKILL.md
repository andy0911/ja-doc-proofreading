# 校正（ja-proofread：書いた後と仕上げ）

4つの段階を、この順で必ず全部通します。途中で止めるときは、どの段階まで終えたかを報告に書きます。

| 段階 | 誰が | 何を見るか |
|---|---|---|
| 1. 機械チェック | スクリプト | 表記ゆれ、台帳の語句と構成の型、文の長さ |
| 2. 独立レビュー | `structure-reviewer` サブエージェント | 構成の型、用語・数字の整合。指摘だけで書き換えない |
| 3. 修正 | あなた | 1と2の指摘を、意味を変えずに直す |
| 4. 読者役テスト | `fresh-eyes-reader` サブエージェント2〜3体 | 理解できるか、信頼できるか、引っかかる所（自由回答） |

最後に、人が確かめる項目の一覧（`../../templates/review-checklist.md`）を本人に渡します。事実と数字の確認は人の仕事で、このスキルでは完了扱いにしません。

スクリプトは、このスキルのディレクトリから見て `../../scripts/` にあります。以下では `<scripts>` と書きます。

## 0. 準備

- 対象のファイルを決めます。スライド（claude.ai の Slides、pptx、Google スライドなど）は、そのままでは textlint にかけられないので、作業用の Markdown に書き出します。1枚を `## スライド番号 見出し` の節にし、本文、表の文字、発表者ノート（`> ノート:` で始める）の順に入れます。書き出したファイルは作業ディレクトリに置き、本人のフォルダには置きません。
- 種類を決めます。スライドや体言止めの多い資料は `slide`、それ以外は `doc` です。プロジェクトに `.ja-proofread.json` があれば、その設定に従います。
- 初回は依存（textlint）を入れます。数十秒かかります。

```bash
node <scripts>/ensure-deps.mjs
```

## 1. 機械チェック

```bash
node <scripts>/proofread.mjs --profile slide 対象.md        # 一覧で見る
node <scripts>/proofread.mjs --profile slide --json 対象.md # 件数を数えるとき
```

- 「必ず」「直したい」「参考」の件数を控えます。報告で修正前と修正後を比べるためです。
- 指摘は候補です。文脈を見て、誤検知なら直さずに記録します（grow-ledger スキルの「誤検知」）。誤検知を記録しないと、効かない型が台帳に残り続けます。
- 本人が過去に自分で書いた文章の基準（`.ja-proofread.json` の `baseline`）があれば、`node <scripts>/stylometry.mjs compare --baseline 基準.json 対象.md` も実行します。結果は目安で、合否には使いません。

## 2. 独立レビュー

`structure-reviewer` サブエージェントを1体起動します。渡すのは次の3つだけにします。書いた経緯や意図は渡しません。先入観なく読ませるためです。

- 対象ファイルのパス
- 台帳のパス（`../../data/ledger.json`）
- 読者は誰か（1行）

返ってきた指摘のうち「台帳にない型」は、6の候補に回します。

## 3. 修正

- 1と2の指摘を直します。意味・数字・出典は変えません。言い換えで事実がずれそうなら、直さずに本人に聞きます。
- 直したら、1の機械チェックをもう一度実行し、件数を控えます。
- 本人の文書を直接書き換えてよいかは、本人の依頼によります。頼まれていなければ、直した版を別に作るか、差分を見せます。

## 4. 読者役テスト（フレッシュアイズ）

`../../templates/reader-test.md` に従って、読者役を2〜3体、別々のサブエージェントとして起動します。

- 1体は必ず「AIの文章に抵抗がある読者」にします。
- 読者役には、対象の本文と人物像だけを渡します。書き手が誰か、AIを使ったか、校正したかは伝えません。
- 理解度の問いは、テストの前にあなたが作り、答えは読者役に見せません。
- 自由回答（引っかかった所、飛ばした所、AIっぽいと感じた所、意味が取れなかった語）を毎回必ず集めます。決まった問いだけでは、台帳にない型が見つかりません。
- 直す前の版と比べたいときは、直す前の版を読む対照の読者役を1体足します。

読者役の指摘で直すべきものがあれば3に戻ります。戻るのは1回までにし、残ったものは報告に書きます。

## 5. 人の確認

`../../templates/review-checklist.md` を、対象に合わせて埋めて本人に渡します。とくに数字・固有名詞・引用・日付は、出典に当たったかどうかを項目ごとに書きます。

## 6. 新しい型の候補

読者役の自由回答とレビューの指摘のうち、台帳のどの型にも当たらないものを候補にします。候補ごとに、名前、例文（本文からの短い引用）、直し方、見つけた経路（読者テスト／独立レビュー／頻度比較／誤検知）を1行でまとめます。

- 本人が台帳を育てることを頼んでいるとき、または `.ja-proofread.json` の `notion.autoRegisterCandidates` が `true` のときは、grow-ledger スキルで Notion の候補データベースに登録します。
- それ以外は、報告に候補を並べ、登録してよいか本人に聞きます。
- 台帳ファイルには直接書きません。台帳に入るのは、本人が Notion で承認した型だけです。

## 7. 報告

結果から書きます。報告に入れるのは次のとおりです。

- 機械チェックの件数（修正前 → 修正後、「必ず」「直したい」「参考」別）
- 独立レビューの指摘件数と、直した件数・直さなかった件数（理由つき）
- 読者役テストの結果（理解度の正答数、信頼度、書き手の推定、自由回答の要点）
- 新しい型の候補と、登録したかどうか
- 人が確かめる項目のうち、まだ確かめていないもの
- 信頼度が低い所（読者役はLLMで、実際の人の反応とは限らないこと、など）

未知の癖をゼロにする保証はありません。報告で「AIっぽさはなくなった」とは書かず、「この手順で見つかったものは直した」と書きます。
